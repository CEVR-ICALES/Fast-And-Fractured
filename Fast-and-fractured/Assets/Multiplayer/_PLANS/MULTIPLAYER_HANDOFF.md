## 0. Why this project stalls

Multiplayer began 2025-06-18 (14 months ago) and has 29 commits touching `Assets/Multiplayer`, with
zero-activity gaps in Oct/Nov 2025 and Jan/Feb/Apr/Jun 2026. Last MP commit: 2026-07-07.

Meanwhile the working tree held **1,728 uncommitted files, +30,100 lines, 135 uncommitted `.cs`
files inside `Assets/Multiplayer` alone** — nearly the entire multiplayer layer, staged but never
committed.

Two consequences drive this whole document:

1. **There was no "done" line.** Without commits nothing is settled, so every session re-opens the

2. **The verify loop is broken.** Verification needs two Unity editors, synchronised, with a human
   driving and shooting. That cannot be coordinated remotely, so fixes ship unverified, the user
   tests, they fail, repeat. Three consecutive sessions ended exactly this way. M1 fixes the loop.

## 2. Architecture in one screen

FishNet **Pro 4.7.2**, host-client (the host is also a player). Everything lives in
`Assets/Multiplayer/` under `FastAndFractured.Multiplayer`; singleplayer has **zero** references
to it.

**Wrapper pattern:** each SP system gets a `Networked*` component that sits alongside it and drives
it, reaching private SP members through `SingleplayerReflectionCache` rather than editing SP. When
you need a new private SP member, add a cached `MethodInfo`/`FieldInfo` there — never a public-ise
patch in SP.

**Movement** is predicted: `NetworkedVehicle` implements `[Replicate]`/`[Reconcile]` over a
`PredictionRigidbody`, and ticks the SP movement state machine from inside `Replicate` via
`NetworkedStateMachineDriver`. **Shooting and damage** are server-authoritative (`NetworkedShoot`,
`NetworkedStatsController`) with local cosmetic projectiles.

### Facts that are easy to get wrong (each cost a full session)

- **`IsOwner` is unreliable on the HOST during and just after spawn.** The server has assigned
  ownership but the host's client half has not processed the spawn. Compare connections instead:
  ```csharp
  bool IsLocalPlayerObject(NetworkObject nob) =>
      nob != null && (nob.IsOwner ||
      (base.LocalConnection != null && nob.Owner != null &&
       nob.Owner.ClientId == base.LocalConnection.ClientId));
  ```
  This was the confirmed root cause of the host-HUD bug. **Assume any other raw `IsOwner` check
  that runs at init time is also wrong.**
- **A `ServerRpc` called from the host can silently no-op** on nested car NetworkObjects (RpcWriter
  runs, RpcLogic never does). Fix: when `IsServerInitialized`, call the server logic directly.
- **FishNet deactivates NetworkObjects while spawning.** So `GetComponentInParent<T>()`
  (active-only) returns null, and *coroutines started in `Awake` are killed, not paused* — they
  never resume and `Awake` never runs again. Always use the `(true)` overload; put post-spawn work
  in `OnStartNetwork`. This was the root cause of "nothing can die to map hazards".
- **Fail SAFE on ownership.** "Could not determine owner" must mean *keep*, never *destroy*.
- **Domain reload is disabled** — every static needs a
  `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` reset or it
  carries state between play sessions.
- **`Physics.SyncTransforms()` syncs Transform → physics engine**, not body → transform. It is not
  a fix for a jittery rigidbody. Tried and removed; don't re-add it.
- **Never write the Transform from the body pose inside `Reconcile()`.** This is the same trap as
  the bullet above wearing a different hat, and it has now cost three regressions. FishNet's
  `RigidbodyState` round-trips in **local** space (`GetState` reads `rb.transform.localPosition`;
  `SetState`, called inside `PredictionRigidbody.Reconcile`, writes `t.localPosition`). With this
  project's `Physics.autoSyncTransforms = false`, `rb.position` at that moment still reports the
  *pre*-reconcile world pose — so `transform.SetPositionAndRotation(rb.position, rb.rotation)`
  reverts the correction that `SetState` just applied. The velocity write survives (velocity lives
  on the Rigidbody, not the Transform), so the signature is: **position never corrects, velocity
  resets to ~0 every reconcile.** Measured live on a client 2026-09-11:
  `PRE_RECONCILE y=215.993 vy=-8.441` → `AFTER_RECONCILE y=215.993 vy=-0.109`; gravity cancelled
  ~44×/s, car hung at y≈216 while the host correctly showed y≈80.
  **Two symptoms, one cause:** trigger colliders follow the *Transform*, not the Rigidbody, so the
  client's car colliders also sat ~136 m above the map — "the client can't pick up interactables or
  trigger TNT" was this same bug, not a second one. If a transform/rigidbody gap looks like the
  problem, log y and vy pre/post reconcile before touching the Transform.
- **`TimeManager._physicsMode` is `Unity`, not `TimeManager`,** while predicted rigidbodies
  reconcile. Suspicious, deliberately NOT changed — reconcile corrections measure ~0.00 cm, so it
  is not the tremble's cause. Note it, don't flip it casually.
- **Rigidbody interpolation must stay `None`** on the vehicles. Setting it to `Interpolate` on the
  owner produced a 140 m transform/rigidbody split. `NetworkedVehicleSetupTests` asserts `None`.
- **Exactly one smoother may write the vehicle transforms.** The car prefabs carry FishNet Beta's
  `NetworkTickSmoother` on `Visuals` + `Turret`, so `NetworkObject._graphicalObject` must stay empty
  and FishNet's built-in `PredictionSmoother` must never spin up. Two smoothers = tremble.

## 4. Open bugs, with everything already known

### BUG-1 — Camera / car tremble on the client — FIXED 2026-08-25, root-caused

**Was never actually the camera.** Three compounding causes, found by instrumenting the live client
via MCP (`execute_code`, not `MpAutoRecorder` — this needed A/B toggles on running components, which
a passive log can't do) instead of theorizing from the car's transform, which is where every earlier
session got stuck (see the old analysis this replaced, in git history if you want it).

1. **`NetworkTickSmoother` on `Visuals`/`Turret` is enabled on the prefab but sits with
   `SmootherController` never started at runtime** — `NetworkedVehicle.ApplyVisualSmoothingForOwnership`
   stops it on purpose (262 m drift measured on 2026-08-12, see that method's own comment). So every
   car has been drawn straight off the physics transform, which only moves on tick boundaries.
   Confirmed live: client renders ~36 fps against a 50 Hz sim tick, so `deltaTime > tickDelta` and
   each frame consumes 1 or 2 ticks alternating — raw per-frame steps read
   `0.105 0.233 0.120 0.228 0.098 0.201`, a clean 1×/2× beat. **Fix:** `VehicleVisualSmoother`
   (`Assets/Multiplayer/VehicleVisualSmoother.cs`) samples the body pose on `OnPostTick`, keyed by
   **tick number, not wall-clock time** (a same-frame multi-tick otherwise stamps two samples
   identically and collapses the interpolant to 1 — this bit an earlier version of the fix and
   shipped silently broken into a build; fixed same day). Draws the graphical children a fixed
   ~2-tick delay behind, interpolated. Attached to all 4 car prefabs via `VehicleSmoothingSetupTool`
   (`Tools ▸ Fast And Fractured ▸ Vehicle Smoothing - Unify`).
2. **The remote player's camera rig was never deactivated.** Each `NetworkedPlayer` carries its own
   `FreeLookCameraLast` (vcam + `CinemachineCollider` + 2 impulse listeners). Two players → two vcams
   at equal priority fighting the one `CinemachineBrain`, plus a second collider raycasting the map
   every frame. Which one wins depends on activation order, which differs host vs. client — this is
   why the symptom only ever showed on one side. **Fix:** `NetworkedLevelControllerWrapper.DisableRemotePlayerCameraRigs()`,
   same fail-safe ownership rule as the HUD pass.
3. **`CinemachineCollider` was configured to oscillate.** `m_MinimumOcclusionTime=0`,
   `m_SmoothingTime=0`, `m_DampingWhenOccluded=0`, `m_Damping=5` — snap in on any occlusion, ease
   back out over 5, re-occlude, snap in again. Measured on the host with the car **completely
   stationary**: camera swung 0.66 m along its own view axis, 0.37 m in a single frame. **Fix:**
   `CameraRigSetupTool` (`Tools ▸ Fast And Fractured ▸ Camera Rig - Fix Collider Oscillation`) retunes
   it and attaches `CameraTargetSmoother`, a per-frame `SmoothDamp` on the Follow/LookAt target — a
   smaller, secondary contributor, but real.

**All three are local/render-side only.** Nothing about the camera or the car's visual pose goes
over the network or touches prediction/reconcile; aiming and turret rotation are untouched.

**Status: fix shipped, not yet watched running by the user in a live match.** Per R4 do not mark B1
verified until someone has. If it still judders after this: check whether turret aiming (applied in
its own `LateUpdate`) runs after `VehicleVisualSmoother`'s (`[DefaultExecutionOrder(-150)]`) and
overwrites its correction — that's the next suspect, untested.

### BUG-1B — Client-only vehicle tremble / "se mueve solo" / excessive speed — FIXED 2026-09-16

A second, unrelated tremble from BUG-1: BUG-1 was the camera/visual layer never touching the
physics body. This one is the physics body itself, on the OWNED car, client-side only. Three
real bugs stacked on top of each other; each was found live, with data, not by theorizing from
the transform.

1. **`IsMovingDecision` had no hysteresis - and once that was fixed, a dead band alone still
   wasn't enough.** `PhysicsBehaviour.IsVehicleMoving()` was `_currentSpeed > isMovingThreshold`
   (0.5 m/s on every car prefab), and that SAME decision asset is wired on both `PlayerIdleState`
   (exit when true) and `GroundedState` (exit when false). Ordinary physics noise at rest (gravity
   settling, reconcile corrections) measured 0.2-0.5 m/s of swing - enough to cross that one line
   constantly. Confirmed in `mp_canary.log` across many sessions, independent of networking: dozens
   of `Grounded<->Idle` transitions per second. Only `GroundedState`'s `ApplyMovementAction` applies
   motor torque, so every Idle flicker was one tick of zero throttle - a real stutter, not just a
   label flapping. **First fix:** `PhysicsBehaviour` remembers its last result and requires crossing
   the OPPOSITE side of a +-0.25 dead band to flip (`MovingHysteresisHalfWidth`). Singleplayer-side,
   but a genuine bug fixed under the "SP may be touched for tests" rule's spirit - it affects
   singleplayer too, MP just surfaces it more because of bug 2 below.
   **The user then confirmed live, playing a real match on `NetworkedMountainVillageMap`, that it
   still trembled after that fix shipped.** Watched `mp_canary.log` update in real time during their
   actual session: `Grounded<->Idle` was STILL flapping every 20-100ms continuously, the whole time.
   A pure hysteresis band cannot help when the real speed doesn't just spike across the line once
   but DWELLS right at one edge of the band for a while (easing off the throttle, climbing a slope
   near stall speed) - a value sitting exactly on the boundary with a little noise still crosses it
   repeatedly. **Second fix, first attempt (same day, corrected within the hour):** a CONFIRMATION
   filter - require `MovingDebounceTicks` (5) consecutive calls agreeing with the candidate value
   before flipping. Live-verified as working (transitions went from continuous sub-100ms flapping to
   a natural ~0.1-1.2s cadence, full-throttle jitter index **0.45** vs a 7.5-16.8 healthy baseline) -
   but a unit test written right after (`VehicleMovingDebounceTests`, added specifically because live
   testing alone had already been shown this session to miss things) caught that this design delays
   EVERY transition by the full window, including a clean one-time "starts moving from a dead stop":
   real added input lag on ordinary driving, not just on noise. **Shipped design: a cooldown
   instead of a confirmation filter.** `_ticksSinceLastFlip` allows a flip to happen on the very next
   disagreeing call (zero added lag for a genuine transition), then blocks any FURTHER flip for
   `MovingDebounceTicks` calls - caps the flap rate instead of delaying every decision.
   **Verified both ways:** `VehicleMovingDebounceTests` (4 EditMode tests - genuine transitions flip
   immediately in both directions, edge-dwelling noise is rate-capped, a flip cannot reverse within
   its own cooldown window) all pass; and live, same map, same reproduction (a deliberately
   weak/near-threshold throttle to force the car to dwell near the line) as the confirmation-filter
   version, transitions are similarly sparse (mostly 100ms+, one 36ms outlier against a ~100ms
   theoretical floor - plausibly two decision evaluations landing in one tick, not a return to the
   original continuous flapping) instead of the original continuous 20-100ms chatter.
2. **`PhysicsMode.TimeManager` causes a live catch-up spiral on this project - do not retry without
   a plan for it.** Tried today on the theory that FishNet's own hard, unconditional reconcile (its
   Rigidbody prediction demo, `Assets/FishNet/Demos/Prediction/Rigidbody`) only looks smooth because
   that mode resimulates physics once per REPLAYED tick, converging the trajectory back to what was
   already predicted. Confirmed live instead: WheelCollider RPM climbed past 130,000 and kept
   climbing (motor torque re-applied and re-simulated every replayed tick, saturating the tire's
   slip curve into pure wheelspin instead of ground force), while `Time.fixedTime` fell 12+ seconds
   behind `Time.realtimeSinceStartup` and did not recover. FishNet bounds the incoming state queue
   (`PredictionManager.RemoveExcessiveStates`) but nothing bounds how many ticks one reconcile's own
   replay loop will run - unbounded here because of WheelCollider tire physics plus
   construction-site colliders. **Reverted to `PhysicsMode.Unity`** (`MultiplayerTimingBootstrap.cs`);
   confirmed RPM recovered from 137,000 to 594 within seconds of switching back.
3. **The soft-reconcile layer that PhysicsMode.Unity needs went through two buggy designs before
   landing on a third, deliberately minimal one.** See `NetworkedVehicle.cs`'s own comment above
   `ApplyServerPose` for the full history (a per-tick pose history caused an 8-teleport burst in
   150ms; a retroactive history rewrite on top of that caused a second, separate runaway). Current
   version compares the server's report against the CURRENT body state (accepting round-trip error
   as noise, which is fine at normal speed) and skips the velocity correction specifically while a
   dash is in flight (`DashTicksRemaining > 0`), since that is the one case where "now" vs "the
   server's slightly-stale report" reads as a large false error. No per-tick history, no retroactive
   rewrites - less code, and everything that broke the first two versions cannot happen here because
   there is no persistent state for a later reconcile to trip over.

**Verified live** via an automated drive+dash+idle harness (see the new MCP recipe in §6) across
three separate rounds on `NetworkedConstructionMap`: jitter index 7.5-16.8 (worst sessions before
today measured 300-400+), owned-car `body/transform` mean 0.002-0.007 m (previously up to several
METRES with `<-- TWO WRITERS FIGHTING`), reconcile corrections mean 0.17-0.66 cm at ~45/s. No
teleport bursts across several minutes of combined automated driving on both peers. The remote
(non-owned, spectated) car occasionally still flags one isolated large `body/transform` sample in a
long window (mean stays tiny, ~0.01-0.05 m) - that looks like FishNet's correct hard-teleport path
doing its job after the other peer moved a real distance between reconciles, not the old bug
pattern (which had a sustained high mean, not an isolated spike). Not re-chased; flag if it turns
into a sustained mean again.

4. **The real player report that came back after all of the above ("menos tembleque pero sigue
   habiendo") had two more, separate causes - both in `NetworkedVehicle.cs`, found live with a
   real dash under `NetworkedVehicleDiagnostics`, not by theorizing:**

   a. **`Reconcile()` was overwriting the client's own gameplay state (`_dashTicksRemaining`,
      steer angle, drift state, etc.) from the server's round-trip-stale report on EVERY reconcile,
      including the ordinary soft path.** `TickDeterministicDash` decrements `_dashTicksRemaining`
      once per tick and expects to own that countdown; a soft reconcile stomping it back to the
      server's older value every ~22ms meant a dash's impulse count kept getting re-topped-up
      mid-dash, measured live at speeds up to 197 m/s vs the server's ~40 m/s. **Fix:** gameplay
      state restoration is now gated behind `restoreGameplayState` (`Reconcile()`), true only for
      non-owned cars (which always follow the server) or when `ApplyServerPose` reports a genuine
      hard snap happened (`ApplyServerPose` now returns `bool`) - an ordinary soft correction no
      longer touches it.
   b. **A second, independent source of the same symptom: `ProcessMovementInput()` (SP) can
      re-trigger `HandleDashWithPhysics()` during a REPLAYED tick.** `HandleDashWithPhysics` only
      re-enters while SP's own `_isDashing` is false, but that flag is owned by a `TimerSystem`
      timer that finishes on WALL-CLOCK time. A reconcile replay revisits ticks whose real-time
      equivalent has already elapsed, so `_isDashing` can read false there even though the MP
      driver's own per-tick counter (`_dashTicksRemaining`) still has the dash in flight -
      `HandleDashWithPhysics` then silently starts a SECOND, frame-rate-driven `TimerSystem` timer
      that stacks its own `AddForce` on top of the one `TickDeterministicDash` already applies once
      per tick. This is what actually produced the 126 m/s spike measured live (dashTicks desynced
      to 56 local vs 28 server at the moment of the spike) - the reconcile hard-snap that followed
      was a symptom of this, not the cause. **Fix:** extracted `OnSpDashStarted`'s "stop the SP
      timer" logic into `StopSpDashTimer()`, now also called every replayed tick while
      `_dashTicksRemaining > 0`, right after `ProcessMovementInput()` - safe to call every tick
      since `TimerSystem.HasTimer` is false once a timer is already stopped, so it only does real
      work the (rare) ticks a rogue timer actually appears.

   **Verified live (2026-09-16):** replayed the exact scenario that produced the 126 m/s spike - a
   2-second HELD dash button (not a tap) from a standstill, the worst case since
   `PlayerInputController` reports dash as a level signal (`.performed`/`.canceled`), not an edge,
   so a real player CAN hold it. Post-fix: ends at ~0 m/s (car came to rest against golf-map
   geometry, not a runaway), zero `HARD SNAP`s during the dash, and a clean 9s steady-state sample
   right after read reconcile corrections at **mean 0.04 cm, largest 0.05 cm** (down from the
   pre-fix session's mean 1.39 cm / largest 35.88 cm measured earlier the same night, itself already
   down from the original bug). Two shorter, more realistic dash taps (~100-120 ms, matching an
   actual button press) both landed at sane speeds (13.91 m/s, 22.56 m/s) with no hard snaps either.
   The temporary `MpCanary.Mark("HARD SNAP ...")` instrumentation added to find this has been
   removed now that the cause is confirmed.

   **Testing note:** verifying this required restarting the match many times - the pre-existing
   "someone can die right at spawn" issue (see the gotcha in §6) hit on more than half of the
   restart attempts during this session, each time ending the match before a sample could be taken.
   Unrelated to this fix; just restart again when it happens, per standing guidance.

5. **Not yet approved by the user - do not call any of the above "fixed" in conversation with them
   until they've verified it themselves.** Continued unattended soak-testing after the three fixes
   above (dash-timer-replay, gated reconcile restore, `IsVehicleMoving` cooldown) turned up one more
   data point worth recording honestly rather than smoothing over: **sustained full-lock steering +
   full throttle for 25+ seconds continuously** (both cars circling in tight loops, not normal
   driving) produced a worse sample than every other test today - owned-car jitter index 89.96, one
   18.5 m single-frame jump, `body/transform` max 20 m (`TWO WRITERS FIGHTING`), and for the first
   time this session the REMOTE (non-owned, spectated) car also flagged it, not just the owned one.
   Checked from the HOST's own perspective during the exact same window: clean (jitter 7.39, zero
   `body/transform` gap on either car) - consistent with the established pattern that this class of
   symptom is a CLIENT-side prediction artifact, never visible on the host. Switching immediately
   back to straight driving on the same client, same session, dropped every number back to the
   healthy range within one sample (jitter 0.08, reconcile mean 0.01 cm). Read together: this looks
   like a real but narrow edge case in continuous hard-lock cornering, not a regression in today's
   three fixes and not the reported trembling (which was reproduced and fixed under ordinary driving
   and dashing) - but it has not been chased to a root cause, and "one client editor hang + relaunch
   happened earlier in this same test window" is a live confound that has not been ruled out either.
   Flag for the user; do not present as understood or fixed.

   **Follow-up (same night): the confound is ruled out - the effect is real and reproduces
   cleanly.** Repeated the identical scenario (full-lock steering + full throttle, ~25s continuous,
   `NetworkedGolfMap` this time) in a fresh session with no editor instability anywhere near the

   above) - but this run did NOT reproduce the 18-20 m single-frame spike or the
   `TWO WRITERS FIGHTING` flag; `body/transform` stayed under the 1 m flag threshold (mean 0.036 m,

   (mean 3.70 cm, largest 17.16 cm) but at a notably LOWER rate (16/s vs the usual ~45/s) alongside a
   lower frame rate (23 fps vs the usual ~38 fps) during the same window - hard cornering may simply
   be more CPU/physics-expensive here (more collision checks, tire slip curve evaluation), which
   would explain both numbers without implicating prediction correctness. Current best read: hard,
   continuous cornering genuinely diverges more between client prediction and server ground truth
   than straight driving (tire slip under lateral load is intrinsically harder to predict exactly),
   so elevated jitter and reconcile magnitude during sustained full-lock turns may simply be the
   REAL, expected cost of predicting a harder physics case - not a bug - while the occasional large
   spike/flag is closer to the already-documented "isolated hard-teleport, not a sustained pattern"
   category from item 3 above. Still not root-caused to the level of a specific line of code, and
   still not something to describe to the user as understood or resolved - but no longer suspected
   of being a testing artifact either.

### BUG-2 — Host cannot use push shoot or ultimate
Host only. The client can use both. Driving and normal shoot work on the host.

**Already tried and did NOT fix it** (`NetworkedLevelControllerWrapper.OnCharactersCustomStartGuard`):
`CarInjector.Install → PlayerInputProvider.Initialize() → BindActions()` runs once per vehicle and
each call creates a new `PlayerInputAction` on the *singleton*. `ChangeShootMode()` TOGGLES
`_isPushShootMode`, so N leaked instances toggle N+1 times per keypress — even ⇒ always false, which
presents exactly as "push shoot does nothing" while `Shoot` (not a toggle) keeps working. The guard
now calls `InputSystem.DisableAllEnabledActions()` then a single `BindActions()`. **The user
reports the bug persists.** So either the leak is re-created after the guard runs, or the cause is
elsewhere. Do not re-derive this theory from scratch.

**Remaining suspects, in order:**
1. The same guard still resolves ownership with a raw `if (nob.IsOwner) continue;`
   (`NetworkedLevelControllerWrapper.cs:493`) — the exact pattern that caused the confirmed host-HUD
   bug. On the host this can be false for its own object, so **the host's own `InputActions` get
   `.Disable()`d**. Apply `IsLocalPlayerObject` here.
2. Something re-binds after the guard. The guard runs on `charactersCustomStart`; anything later in
   init that touches `PlayerInputProvider.Initialize()` re-leaks.

**Live anomaly captured:** the *remote* player's `PlayerInputController` (root index 1,
`IsOwner=False`) was `enabled=False` **but had `IsPushShooting=True` stuck**, while the host's own
(index 0) was `enabled=True` and was what `PlayerInputController.Instance` pointed at.

**Do not fix this blind — this bug has already survived two blind fixes.** Get a recording (§6)
showing whether the host's keypress reaches `PlayerInputProvider` and whether the toggle count is
even, then fix what it shows.

**Mechanism found live, 2026-09-16 (not yet fixed - needs a real second keyboard to verify):**
`PlayerInputController` is instantiated PER CAR (confirmed live: exactly 2 live instances in a
2-player match, one per `NetworkedPlayer` root), not once per scene as its `AbstractSingleton<T>`
base assumes. `AbstractSingleton<T>.HandleDuplicate()` resolves the collision by construction
ORDER ONLY - whichever instance's `Construct()` ran first stays `enabled`, the second is disabled -
with **zero awareness of ownership**. In the live match checked, the surviving (enabled) instance
happened to belong to the connection whose car spawned first, which happened to be the local
player - so push shoot/ultimate worked in that specific test purely by luck of spawn order, not
because the mechanism is correct. Confirms the earlier "even toggle count" theory was diagnosing a
symptom of the SAME root class of bug already found and fixed elsewhere in this project (the
host-HUD bug, the camera-rig bug): an SP singleton's generic conflict-resolution logic has no
concept of "which one is ME" once two copies exist in one process, same as `AbstractSingleton<T>`
here.

The general fix (matching this project's own established rule: fail-safe on ownership) would be
making `HandleDuplicate()` - or a caller of `ClaimSingletonOwnership()` - prefer the instance whose
GameObject hierarchy has an owned `NetworkObject`, instead of first-constructed-wins. NOT attempted
tonight: `AbstractSingleton<T>` is shared base infrastructure used by many singletons across the
whole project (SP included), and this class of fix cannot be verified without a genuine second
keyboard/player driving a live match - a synthetic/reflection-driven input test cannot tell you
whether a REAL keypress reached the right instance, only whether the states LOOK plausible. Per R4,
recorded as a precise, actionable lead rather than shipped blind.

### BUG-5 — Mines and push bullets fell through the map — FIXED 2026-08-25
`NetworkedProjectile`'s collision sweep used
`LayerMask.GetMask("Default","Characters","Ground","Obstacles")`. No layer named `"Obstacles"`
exists in this project; `GetMask` silently contributes nothing for an unknown name. `Static` (722
colliders on MountainVillage, vs. 3 on `Ground`) was never in the mask, so a mine swept straight
through the level. **Fix:** the mask is now derived from the project's own layer collision matrix
for the projectile's layer, so a future renamed/missing layer can't silently vanish again. Also
fixed in the same commit: the sweep now ignores triggers (it stands in for `OnCollisionEnter`,
which never fires against one); a landed mine now writes its rest position instead of freezing
wherever the previous tick left it; and a client-side mine no longer permanently hides itself
because the freeze branch was gated on `IsServer`. Singleplayer's `PushBulletBehaviour` had the same
freeze bug from a different cause (`rb.constraints = FreezePosition;` immediately overwritten by
`rb.constraints = FreezeRotation;` on the next line) — fixed alongside it.
**Not yet re-verified live**, per R4.

## 6. Tooling

### Two editors
The main project is the **host**. A **ParrelSync clone** is the second editor, configured
client-role: its start button calls `ClientManager.StartConnection` and it *cannot* solo-host.

### MCP
stdio server `UnityMCP`. **Host = port 6400, clone = 6401.** Pass `unity_instance="6400"` /
`"6401"` per call, or pin with `set_active_instance`.

`execute_code` runs through codedom wrapped as `public static object Execute() { <your code> }` —
so **use `return`**, and **fully qualify types**. Known quirks: `System.Action` will not convert to
`UnityEvent`'s `UnityAction` (declare `UnityEngine.Events.UnityAction`); `FastAndFractured.CarInjector`
and `FastAndFractured.Controller` do not resolve — go through reflection; `nm.PredictionManager` is
inaccessible — use `FindFirstObjectByType`.

### Driving a match from MCP — direct-connect recipe (2026-09-16, preferred)

Skips Steam, the lobby UI, and every flaky button below entirely. Bypasses
`LobbyServiceLocator`/`SteamLobbyTransport` (the Steam-lobby layer) by talking straight to the
`Tugboat` transport that FishNet's `TransportManager` actually wraps underneath it — Steam lobby
creation was the one step in this whole flow that proved flaky/slow enough to be worth skipping for
automated testing (see the `AskFeedbackDialog` gotcha below for the *other* thing that made Steam's
layer look broken when it wasn't).

```
HOST : manage_editor play
       var nm = FishNet.InstanceFinder.NetworkManager;
       var tugboat = nm.TransportManager.Transport as FishNet.Transporting.Tugboat.Tugboat;
       tugboat.SetPort(7779); nm.ServerManager.StartConnection(); nm.ClientManager.StartConnection();

CLONE: manage_editor play
       var tugboat = nm.TransportManager.Transport as FishNet.Transporting.Tugboat.Tugboat;
       tugboat.SetClientAddress("127.0.0.1"); tugboat.SetPort(7779);
       nm.ClientManager.StartConnection();

HOST : var lobby = FindFirstObjectByType(typeof(NetworkedLobbyManager));  // via reflection, see below
       // ServerSelectCharacter(string, NetworkConnection) and ServerSetReady(bool, NetworkConnection)
       // are public but need an explicit NetworkConnection per player - loop nm.ServerManager.Clients
       // and call both for each. Then force the match start directly instead of waiting on the
       // ready/countdown wiring (which did not fire reliably from a reflection-set SyncDictionary):
       var startInternal = lobbyType.GetMethod("StartGameInternal", NonPublic | Instance);
       startInternal.Invoke(lobby, null);
       // wait ~10s for the map-vote slot animation + FishNet's LoadGlobalScenes
```

All types not directly resolvable from `execute_code` (`NetworkedLobbyManager`,
`NetworkedVehicle`, `NetworkInputProvider`, ...) — go through
`System.Type.GetType("FastAndFractured.Multiplayer.X, Assembly-CSharp")` + reflection, same as the
existing MCP quirks note above.

**Driving a car once spawned, without a human:** swap the owned car's `InputProvider` for a fresh
`NetworkInputProvider` (`gameObject.AddComponent`, `_localProvider` stays null so it reads whatever
you feed `SetNetworkInput(VehicleInputData)` directly — `MoveInput`, `AccelerateInput`,
`HandbrakeInput`, `DashInput`), same technique `NetworkedVehicle.Replicate` already uses for
observed players. **Restore control afterward**, or the real player's input is silently ignored:
`Destroy` the added component, then call `NetworkedVehicle.ApplyInputProviderLocally()` (public) to
re-find and re-wire the REAL provider, which lives on the car's PARENT, not the car itself
(`GetComponentInParent<NetworkInputProvider>()` in that method — a same-session `GetComponent` on
the car itself will find your own test component instead and "restore" the wrong one).

**Gotchas that cost hours:**
- **`ParrelSync`'s `AskFeedbackDialog` fires a BLOCKING modal (`EditorUtility.DisplayDialogComplex`)
  after ~20 domain reloads in a session** (`Assets/ParrelSync/Editor/NonCore/AskFeedbackDialog.cs`).
  A modal dialog stops the Editor's main thread cold — MCP calls time out, `mp_canary.log`'s
  heartbeat stops, and it looks exactly like a hang or a `PhysicsMode.TimeManager`-style spiral. A
  session with many recompiles (any active bugfixing session) WILL cross this. Disable it once,
  permanently, on every instance you'll drive from MCP:
  `EditorPrefs.SetBool("ParrelSync_StopShowFeedBack", true)`.
- Check `transport.GetConnectionState(true)`, not just `InstanceFinder.IsServerStarted`.
- **A leftover server on the same port is not released between matches** — stop the previous play
  session (`manage_editor stop`) or pick a different port before reconnecting.
- Any blocking MCP call freezes Unity's main thread, so held keys / sustained input via the real
  Input System releases mid-call. Use the `NetworkInputProvider` swap above instead — it is a plain
  field write, not a held key, so it survives blocking calls on either side.
- **Never `Stop-Process` an editor in Play Mode** — the next launch hangs for minutes on "Recovering
  Scene Backups". Use `manage_editor stop`, then restart. If a hard restart is unavoidable (a real
  hang, not the `AskFeedbackDialog` one above), get the exact exe + project path first:
  `System.Diagnostics.Process.GetCurrentProcess().MainModule.FileName` /
  `Application.dataPath` from the SAME instance while it still responds, since you cannot ask a
  hung one.
- If the host editor OOM-crashes, `CreateLobbyAsync` silently fails to start the server afterwards.
  Workaround: `tp.SetPort(7777); nm.ServerManager.StartConnection();` then
  `nm.ClientManager.StartConnection()` (this is now just the direct-connect recipe above).
- **Do not rapid-fire reconnect/rematch cycles within the same play session to "test more."** Doing
  5 connect→match→(die or disconnect)→reconnect cycles in a few minutes on a fresh port each time
  (2026-09-16) produced dozens of `Object Id [N] already exists within ObjectId Cache` errors and one
  instant, wrong `YOU WON!` resolution - FishNet's spawned-object ID cache from an earlier
  cycle was still warm when the next one started spawning, inside the SAME Unity process. This is
  a testing-methodology artifact, not a gameplay bug: no real player session does this. If a
  connect/match cycle produces `ObjectId Cache` errors or a suspiciously instant win/loss, that is
  the signature - `manage_editor stop` (a full stop, not just tearing down the FishNet connection)
  before the next cycle, and treat what happened during the contaminated cycle as unverified, not as
  a new bug to chase.
- **A player can die right at spawn, before doing anything.** Confirmed by the user as a known,
  pre-existing, separate issue - not something to investigate, just restart the match
  (`[NetworkedStatsController] ... killed by Unknown` seconds after spawn, in `mp_canary.log` or the
  console). Hit repeatedly during this session's testing (more than half of ~8 restart attempts on
  2026-09-16). One restart in this session also showed a `NullReferenceException` at
  `MultiplayerPauseGate.cs:56` immediately after a new match's scene loaded, preceded by "Some
  objects were not cleaned up when closing the scene ... PauseManager" - a leftover `PauseManager`
  singleton surviving match teardown into the next match's init. Same root-cause class as BUG-2's
  `AbstractSingleton<T>` construction-order note above (not the same singleton, but the same
  base-class mechanism). Not fixed - noted here in case it turns out to be a contributor to the
  spawn-death issue rather than a coincidence; needs its own live investigation to confirm either
  way.

BUG-1 and BUG-2 have each survived multiple attempts because nobody has watched them fail with

   push shoot and ultimate on the host — then read both `MpAutoRecord.log` files. That single
   artifact should settle BUG-2 outright and point at the right subsystem for BUG-1.
2. **Fill `Tests/Runtime/`.** It is empty. Add FishNet play-mode tests that spin a host and a fake
   client in one editor for everything that doesn't need a human: spawn/ownership resolution, the

4. **B3, B9, E2, A6, A7** — cheap individual checks.
5. **E4 latency** via the network-sim controls in `MultiplayerToolsHub`. Two local editors have ~0 ms
